## Facts

- 224 concurrent HTTP clients fail the 350 ms gate.
- No request returns an error. The model RTF stays below 1.0.
- The client sees the first chunk about 3.3 s later than the server sends it.
- The server waits 1.2 to 2.9 s in the queue before a job starts.
- The batch first emit is about 570 ms after a job starts.

## Guesses

- The gap between server and client time is CPU contention. The server process and the async probe client share 4 vCPU.
- Head-of-line blocking adds the queue tail. A job that arrives after a batch starts waits for that batch to finish.

## Assumptions checked

ASSUMPTION A-30 (224 clients need a row-based admission rule) — PARTLY CONFIRMED. A drain rule fills the batch, but a job that arrives after the batch starts still waits for the full batch.

## Tried

1. Set client limits to 256. Result: removed the probe client-limit artifact.
2. Use one async client and a start barrier. Result: removed the thread ramp.
3. Warm the connection pool. Result: no stable gain.
4. Drain all waiting jobs before the window. Result: batch fill improved, tail stayed.
5. Use one conditioned profile. Result: server p95 fell from 3166 to this run, but the gate still fails.

## Open question for planner

The remaining delay is not model compute. The direct B=224 batch first emit is 98 ms. Choose one:
1. Admit new rows into a running batch (continuous batching) to remove head-of-line blocking.
2. Move the load generator to a separate host, and set the gate on server `request_first_chunk_ms`.
3. Descope 224 concurrent clients for one 4-vCPU T4 host.
